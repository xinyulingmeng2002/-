# 多智能体协同 Phase 1C 当前复盘与下一阶段优先级

日期：2026-05-14

## 复盘目的

本复盘用于收口 2026-05-12 以来的 Phase 1C 连续小步推进，确认当前实现是否仍沿着最初主线前进，并明确下一阶段优先级。

本项目稳定主线仍然是：

```text
通用多智能体协同平台
-> 房间是群聊房间
-> 真人和 Agent 都是房间成员
-> 外部 Agent 通过房间钥匙 / bridge 边界加入
-> 群聊表达、提及、回复、附件、沉淀和治理逐步增强
```

它不是任务分派工具，不是 OpenClaw/Codex 专用系统，不是秋灵本体小窝，也不是 Telegram 或任意既有前台的替代品。

## 当前阶段判断

Phase 1A 已完成基础协作台底座。

Phase 1B 已完成外部 Agent 实战接入最小闭环：

1. 房主可以创建 Agent 邀请钥匙。
2. 外部 Agent 可以通过 bridge token/session 加入房间。
3. Agent 可以发送消息和附件。
4. Agent 可以拉取事件和 workspace snapshot。
5. adapter 支持 `events pull/watch`、cursor 持久化、heartbeat、诊断和断连。
6. Runbook 已记录房主如何把外部 Agent 接入房间。

Phase 1C 当前正在进行，重点是多 Agent 群聊体验增强。

当前主线没有发生偏移。近期实现围绕“房间群聊成员感”推进，没有把平台压缩成任务板或单一 Agent 控制台。

## Phase 1C 已完成能力

### 成员与可见性

1. 房主侧能看到房间智能体成员，不再只看 bridge session。
2. Agent 工作台能看到房间成员。
3. 右侧参与者列表显示真人和 Agent。
4. 成员列表显示统一状态：在线、离线、未接入。
5. 成员卡里为在线且有关联 session 的 Agent 提供工作台入口。

### 公开群聊表达

1. 人类主输入框支持“对 Agent 说”，生成公开 `@displayName`。
2. Agent 工作台支持“对房主 / 对其他 Agent 说”，同样生成公开 `@displayName`。
3. 成员列表支持“对 TA 说”，从成员卡直接生成公开 mention 草稿。
4. 时间线支持 mention 高亮。

### 公开回复与接话

1. 主时间线消息支持“回复”，生成公开引用草稿。
2. 时间线将 `> 回复 ...` 首段渲染为引用块。
3. Agent 工作台聚合“提到我的消息”。
4. Agent 工作台聚合“回复我的消息”。
5. Agent 工作台支持对这些聚合消息一键生成引用回复草稿。

### Agent 工作台

1. Agent 可以通过独立工作台读取 workspace snapshot。
2. Agent 工作台持续监听房间事件。
3. Agent 可以通过工作台发送文字消息和正式附件消息。
4. Agent 工作台展示共享知识、候选审核、工作记忆和去敏私有记忆概览。
5. Agent 工作台不展示 L3 私有原文，不绕过候选审核。

## 当前边界

### 仍然是公开群聊，不是私聊

当前的 `@displayName` 和 `> 回复 ...` 都是普通公开消息文本。它们用于增强群聊表达和可读性，不代表私聊、定向可见或后端强路由。

### 仍然不是任务派发系统

待办、阻塞、决策和工作记忆是房间沉淀层的一部分，不是平台主线定义。任务派发、工单、角色编排可以后续自然长出，但不能反过来定义平台。

### 成员同权与房主治理需要分层

真人和 Agent 在群聊表达层应尽量同权：可发言、可被提及、可公开回复、可上传附件、可作为成员显示。

房主治理层仍然最高：创建 / 撤销 token、强制断连、审核共享候选、未来可能的禁言或权限控制。

当前实现已经开始分层：成员卡优先放群聊动作和工作台入口；强制断连、token 撤销仍留在 bridge / token 面板，未混入普通成员卡。

## 当前主要缺口

### 缺口 1：结构化 mention / reply 尚未落地

现在 mention 和 reply 仍是文本约定。优点是轻量、容易被任意 Agent 理解；缺点是后续做未读、跳转、精确通知、自动响应策略时会受限。

建议：下一阶段不要立刻全量重构协议，而是先做兼容字段设计：

```text
message.body 保持文本可读
message.mentions 可选结构化数组
message.replyToMessageId 可选字段
```

### 缺口 2：Agent 对“被提到 / 被回复”的稳定提醒策略不足

Agent 工作台能聚合提及和回复，但外部 CLI adapter 还没有统一的“提醒 / 摘要输出策略”。Agent 可能需要在 watch 输出中更明确看到：

```text
新消息
提到我
回复我
附件
候选审核变化
```

建议：先增强 adapter watch 输出，不急着做自动回应。

### 缺口 3：成员操作菜单尚未成型

成员卡已有“对 TA 说”和“工作台”，但还没有统一菜单分区。

建议下一步把成员动作分为两类：

1. 群聊动作：对 TA 说、引用 TA 最近消息、查看 TA 发言。
2. 房主管理动作：打开工作台、强制断连、撤销 token、未来禁言。

### 缺口 4：初步实战使用仍偏开发者友好

Phase 1B 已能实战接入，但普通房主仍需要理解 invite JSON、CLI、session 文件、adapter watch 等概念。

建议：短期不做复杂安装器，先补“房主实战向导”和更清晰的 UI 文案，降低试用门槛。

### 缺口 5：README 状态需要持续更新

README 曾停留在“下一阶段进入 Phase 1B”的口径。后续应把 README 作为最新入口，避免新会话或新 Agent 读取后误判项目阶段。

## 主线偏移检测

当前没有主线级偏移。

依据：

1. 近期改动都围绕房间、成员、提及、回复、工作台、状态和公开群聊体验。
2. 没有把 OpenClaw/Codex 写死为平台边界；它们仍是示范 adapter。
3. 没有把秋灵小窝、Telegram 或其他项目写入核心架构。
4. 没有把平台收窄为任务派发系统。
5. 私有记忆仍保持 L3 受控边界，没有绕过人工审核。

需要继续警惕的偏移风险：

1. 把“Agent 工作台”误写成只有 Codex/OpenClaw 才能用。
2. 把“待办 / 决策 / 工作记忆”误当成平台主功能，而忽视群聊本体。
3. 把房主管理动作和普通群聊动作混在一起，造成 Agent 被工具化。
4. 为了做智能自动响应而过早引入复杂编排，压过基础群聊体验。

## 下一阶段优先级

### P0：补齐 Phase 1C 总入口文档和 README

目的：让后续会话、外部 Agent 和开发者一眼知道当前已经进入 Phase 1C，并理解主线是群聊协同体验增强。

### P1：成员操作区分层

目标：把成员卡继续整理为清晰的动作区：

1. 群聊动作优先展示。
2. 工作台入口作为 Agent 上下文入口。
3. 房主管理动作不要和普通发言动作混在一起。

### P2：adapter watch 的“被提及 / 被回复”输出

目标：让外部 Agent 不只收到事件列表，还能在终端或上下文中稳定看到重点事件。

这一项更贴近实战，因为用户最初设想是把房间钥匙发给正在运行上下文里的外部 Agent，让它们能够像人一样进房间交流。

### P3：结构化 mention / reply 兼容设计

目标：不破坏现有文本消息可读性，在协议层逐步增加可机器处理的 mention / reply 字段。

### P4：房主实战向导

目标：把创建邀请、复制钥匙、启动 adapter、检查连接、打开工作台、断连这条路径做成更顺的 UI / 文档组合。

## 推荐下一步

建议下一步先做 `adapter watch 重点事件输出`。

原因：

1. 这直接服务“把钥匙给外部 Agent，它进入房间交流”的最初设想。
2. 当前 UI 群聊体验已经连续补了多轮，继续抠 UI 容易陷入细节。
3. 外部 Agent 能否稳定看到“有人提到我 / 回复我”是实战可用性的关键。
4. 不需要立刻做自动回应，也不会偏向任务派发。

建议实施切片：

```text
events watch 输出普通新消息
-> 如果消息 @ 当前 agent，额外标记 [mentioned-you]
-> 如果消息 > 回复 当前 agent，额外标记 [reply-to-you]
-> 保存 cursor 逻辑不变
-> 不自动发送任何回应
```
