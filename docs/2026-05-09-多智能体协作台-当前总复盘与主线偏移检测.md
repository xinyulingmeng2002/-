## 最初设想的稳定主线

当前可确认的稳定主线如下：

1. `09-多智能体协作台` 是独立项目，不是小窝本体重构，也不是 OpenClaw 附庸
2. OpenClaw、Codex、Claude 等外部 Agent 通过 bridge / adapter 接入，不应被写死进平台核心
3. 平台核心目标是长期运行的房间式多 Agent 协作底座
4. 人类、Agent、bridge、system 必须有清晰身份边界
5. 原始消息、附件与事件先保真进入 `L1`，再派生摘要、工作记忆、共享知识与私有记忆
6. 附件必须是正式 `message + attachments` 模型，不退化成正文里的 URL
7. `L3` Agent 私有记忆默认不暴露，进入共享层必须经过候选与人工审核
8. 当前阶段先求可运行、可追踪、可验收，不做自动自治、向量检索、登录权限体系或复杂多媒体通话

## 与秋灵 / 小窝 / OpenClaw 的关系

从 Codex 记忆与项目文档可以确认：

1. `F盘小窝` 仍是秋灵本体主根；本项目只是旁侧协作底座
2. OpenClaw 是参考生态 / 桥接层，不是秋灵本体，也不是本项目核心
3. Telegram 前台线、小窝家 UI 线、Codex 后台协作线不能混成一条
4. 多智能体协作台可以为这些系统提供房间、事件、附件、候选、共享知识等协作基础设施，但不替代它们

这意味着：本项目当前应该继续建设“协作底座与 bridge 边界”，不应转向重做小窝 UI、Telegram 前台或 OpenClaw 内部运行时。

## 主线偏离状态检测

结论：当前没有发生主线级偏移。

理由：

1. 核心仍是独立协作平台，而不是小窝本体重构
2. OpenClaw / Codex 仍是 adapter，不是 canonical state
3. 消息、附件、事件仍以平台服务端为事实中心
4. `L3` 私有记忆没有被普通公共面板直接公开
5. 候选和共享知识仍需要人工确认
6. 最近修复集中在验收发现的基础体验问题，没有把项目拉向无关方向

需要继续警惕的偏移风险：

1. 公共右侧面板继续无限膨胀，变成混杂后台管理台
2. 过早做 embedding、自治学习、自动上浮，破坏人工审核边界
3. 把 OpenClaw 或 Codex 的内部协议写死进平台核心
4. 把多智能体协作台当成小窝 UI 替代品推进
5. 为了演示方便绕过 `L3` 私有记忆权限边界

## 下一步建议

推荐下一阶段不是继续扩大公共面板，而是从 `main` 新开独立分支做：

`Phase 1B 后续：Agent 专用工作入口 / 真实 bridge 接入体验`

该阶段应该优先解决：

1. Agent 如何稳定接入并保持在线
2. Agent 如何拉取房间事件与当前工作上下文
3. Agent 如何提交候选、私有记忆和状态回写
4. 人类如何看到 Agent 当前是否在线、在哪个房间、最近做了什么
5. Agent 专用入口与普通公共面板如何隔离，避免权限复杂度继续压进右栏

不建议下一步做：

1. 登录/权限大系统
2. 向量检索
3. 自动学习
4. 大规模 UI 重设计
5. 小窝本体或 Telegram 线接管
