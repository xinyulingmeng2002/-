## 最初设想的稳定主线

当前可确认的稳定主线如下：

1. `09-多智能体协作台` 是通用多 Agent 协作平台，不是小窝本体重构，不是 OpenClaw 附庸，也不是 Telegram 前台或任何既有系统的扩展页
2. 项目文件夹只是物理上放在 `/mnt/f/ClawWorkspace/` 根目录附近；它与秋灵本体小窝没有架构从属、业务绑定或运行态耦合
3. OpenClaw、Codex、Claude 等外部 Agent 只通过 bridge / adapter 接入；OpenClaw 与 Codex 是首批示范适配器，不代表平台目标被限定为这两个运行时
4. 平台核心目标是长期运行的房间式多 Agent 协作平台，用户可以创建多个聊天空间，并按需要接入一个或多个 Agent
5. 人类、Agent、bridge、system 必须有清晰身份边界
6. 原始消息、附件与事件先保真进入 `L1`，再派生摘要、工作记忆、共享知识与私有记忆
7. 附件必须是正式 `message + attachments` 模型，不退化成正文里的 URL
8. `L3` Agent 私有记忆默认不暴露，进入共享层必须经过候选与人工审核
9. 当前阶段先求可运行、可追踪、可验收，不做自动自治、向量检索、登录权限体系或复杂多媒体通话

原始会话中的关键口径包括：

1. 用户提出的是“隔离与其他所有的单独的一个平台”
2. 平台应支持新建多个聊天空间
3. 多个 Agent 可通过链接、令牌、API 或后续更底层的接入技术加入当前会话 / 房间
4. 多模态能力包括文件、图片、视频、语音、动图等，但首版优先把房间、多参与者、身份边界和消息链路搭稳
5. 我当时给出的项目位置说明是“只是在 `/mnt/f/ClawWorkspace/` 根目录下新建一个独立项目文件夹，和小窝现有本体、秋灵体系、`00-系统框架/小窝` 都不发生耦合，只是物理上放在同一空间里”

## 与秋灵 / 小窝 / OpenClaw 的边界

从 Codex 记忆与项目文档可以确认：

1. `F盘小窝` 是另一条项目线中的秋灵本体主根；`09-多智能体协作台` 不属于小窝本体的一部分
2. 本项目与小窝的关系仅是目录位置相邻，不共享本体定义、运行态、业务目标或数据主权
3. OpenClaw 与 Codex 是首批用来验证接入模型的示范 adapter，不是平台核心，也不是平台存在的原因
4. Telegram、小窝家 UI、OpenClaw 内部运行态都不应被写进平台核心主线；如果未来需要接入，也应作为普通外部 adapter 处理

这意味着：本项目当前应该继续建设“通用房间式协作平台 + 可扩展 Agent 接入边界”，不应转向重做小窝 UI、Telegram 前台、OpenClaw 内部运行时，也不应把这些系统视作本项目的默认服务对象。

## 主线偏离状态检测

结论：当前没有发生主线级偏移。

理由：

1. 核心仍是独立通用协作平台，而不是小窝本体重构、Telegram 前台或 OpenClaw 附属组件
2. OpenClaw / Codex 仍是首批 adapter 示例，不是 canonical state，也不是平台边界
3. 消息、附件、事件仍以平台服务端为事实中心
4. `L3` 私有记忆没有被普通公共面板直接公开
5. 候选和共享知识仍需要人工确认
6. 最近修复集中在验收发现的基础体验问题，没有把项目拉向无关方向

需要继续警惕的偏移风险：

1. 公共右侧面板继续无限膨胀，变成混杂后台管理台
2. 过早做 embedding、自治学习、自动上浮，破坏人工审核边界
3. 把 OpenClaw 或 Codex 的内部协议写死进平台核心
4. 把多智能体协作台当成小窝 UI、Telegram 前台或 OpenClaw 内部运行态的替代品推进
5. 为了首批示范适配器方便，牺牲“任意 Agent 可按统一边界加入房间”的通用性
6. 为了演示方便绕过 `L3` 私有记忆权限边界

## 下一步建议

推荐下一阶段不是继续扩大公共面板，而是从 `main` 新开独立分支做：

`Phase 1B 后续：Agent 专用工作入口 / 真实 bridge 接入体验`

该阶段应该优先解决：

1. Agent 如何稳定接入并保持在线
2. Agent 如何拉取房间事件与当前工作上下文
3. Agent 如何提交候选、私有记忆和状态回写
4. 人类如何为房间选择、邀请、启用或移除不同 Agent
5. Agent 专用入口与普通公共面板如何隔离，避免权限复杂度继续压进右栏
6. Codex / OpenClaw 适配器如何继续作为示范实现存在，而不把平台协议收窄成专用协议

不建议下一步做：

1. 登录/权限大系统
2. 向量检索
3. 自动学习
4. 大规模 UI 重设计
5. 小窝本体、Telegram 线或 OpenClaw 内部运行态接管
