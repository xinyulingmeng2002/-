# 多智能体协作台 附件消息设计规格

- 日期：2026-04-30
- 项目路径：`/mnt/f/ClawWorkspace/09-多智能体协作台`
- 上游规格：`docs/2026-04-15-多智能体协作台-设计规格.md`
- 当前目标：把“上传附件”从系统提示 URL 提升为房间时间线里的正式消息卡片

## 2026-05-09 状态更新

本规格目标已经在当前 `main` 中完成：

1. Web 上传后创建正式附件消息
2. `/api/messages` 支持正文、附件、正文加附件三种形态
3. 附件会绑定 canonical `messageId`
4. 时间线按图片卡片或文件卡片渲染
5. `/uploads/...` 可以直接访问上传文件
6. 图片预览使用受控缩略图，不再撑满消息卡

本文件保留为附件消息设计记录，不需要重新执行同名计划。

## 1. 背景与问题

当前平台已经具备：

1. 附件上传接口
2. 房间消息事件流
3. Web 时间线展示
4. Bridge 侧消息 ingress / egress

但上传链路仍有明显断层：

1. 上传完成后，Web 只是追加一条“已上传 xxx，可通过 URL 访问”的系统提示
2. 附件没有进入 canonical message pipeline
3. 时间线不能把附件当作正式消息渲染
4. bridge 与人类消息无法共享统一的附件语义

这会导致平台看起来像“能传文件”，但并没有真正形成“附件消息”。

## 2. 本次目标

本次只补齐“上传即发正式附件消息”闭环：

1. 上传成功后，立即作为一条正式聊天消息进入房间时间线
2. 图片类附件在时间线中直接预览
3. 普通文件以文件卡片形式展示
4. 附件消息进入 canonical message pipeline，与普通文本消息共享同一事实来源
5. 后续 bridge 发出的附件消息可以复用同一套数据结构与前端渲染

## 3. 本次不做

明确不进入本次范围：

1. 输入框待发送附件队列
2. 用户补正文后再一并发送
3. 多附件拖拽与批量管理
4. 图片灯箱或全屏浏览器
5. 缩略图生成与媒体转码
6. 附件权限签名 URL
7. 摘要系统理解附件内容

## 4. 方案比较

### 方案 A：扩展现有 `/api/messages`

流程：

1. `uploadFile()` 继续只负责持久化文件并返回附件草稿元数据
2. 前端上传成功后立即调用 `createMessage()`
3. `createMessage()` 支持把附件草稿一并写入正式消息
4. 服务端为附件绑定 canonical `messageId`

优点：

1. 保持单一消息通路
2. 文本消息与附件消息语义统一
3. 未来支持“正文 + 附件”最自然
4. bridge ingress 也能复用同一消息结构

缺点：

1. 要扩展协议、消息路由、时间线类型和测试

### 方案 B：新增“上传即发”专用接口

例如 `/api/rooms/:roomId/attachments` 一次请求同时完成上传和发消息。

优点：

1. 前端调用非常直接

缺点：

1. 上传语义与消息语义耦合
2. 不利于 bridge 侧复用
3. 以后支持“正文 + 附件”时还要回头整理消息模型

### 方案 C：引入独立 `attachment.created` 事件

优点：

1. 对现有文本消息接口改动较小

缺点：

1. 时间线语义分叉
2. bridge、摘要、前端都要维护额外分支
3. 平台事实来源会从“消息流”变成“消息 + 附件双流”

## 5. 选型结论

本次采用方案 A：

1. 扩展现有 `/api/messages`
2. 附件消息仍然是 `message.created`
3. 消息 payload 允许同时携带 `body` 与 `attachments`
4. 首版 Web 行为是“上传后立即发送”，正文默认为空

这样可以让首版产品行为很简单，同时保留未来自然演进空间。

## 6. 数据模型

### 6.1 Attachment Draft

上传接口返回的附件草稿数据，用于给正式消息附带引用。

字段：

1. `id`
2. `messageId`
3. `kind`：`image` / `file` / `link`
4. `url`
5. `name`
6. `mimeType`
7. `sizeBytes`

约束：

1. `uploadFile()` 返回时 `messageId` 为空字符串
2. 只有进入正式消息后，服务端才会把 `messageId` 绑定为 canonical message id

### 6.2 Message Payload

`message.created.payload` 扩展为：

1. `messageId`
2. `speakerParticipantId`
3. `body`
4. `attachments?`

约束：

1. `body` 可以为空字符串
2. `attachments` 可以为空数组或省略
3. `body` 与 `attachments` 至少有一个存在

## 7. 接口行为

### 7.1 上传接口

`POST /api/uploads`

保持职责不变：

1. 接收单个文件
2. 持久化到上传目录
3. 返回附件草稿元数据

返回结构新增：

1. `attachment.name`
2. `attachment.mimeType`
3. `attachment.sizeBytes`

这样前端渲染卡片时不必再额外拼接上传响应的外围字段。

### 7.2 消息创建接口

`POST /api/messages`

新规则：

1. `roomId` 必填
2. `speakerParticipantId` 必填
3. `body` 可为空
4. `attachments` 可选
5. 若 `body` 为空且 `attachments` 缺失或为空，则返回 `400`

服务端职责：

1. 生成 canonical `messageId`
2. 将传入附件复制为正式消息附件
3. 给所有附件补上同一个 `messageId`
4. 把完整 payload 写入事件日志
5. 继续更新工作记忆与摘要

## 8. 前端时间线表现

### 8.1 总体原则

1. 附件消息仍然是 `chat` 消息，不新增独立事件卡类型
2. 消息头部继续展示 speaker 与时间
3. 消息正文为空时，不渲染空白文本段落
4. 附件渲染位于消息主体区域

### 8.2 图片附件

采用用户确认的 `A` 方案：

1. 图片预览直接占据卡片主体
2. 下方显示文件名、MIME、大小
3. 提供“查看原图”链接

### 8.3 普通文件附件

1. 显示统一文件卡片
2. 展示文件名、MIME、大小
3. 提供打开或下载链接

## 9. Web 交互流程

上传按钮点击后：

1. 选择文件
2. `uploadFile()` 上传并获得附件草稿
3. 前端立即调用 `createMessage()` 发送正式附件消息
4. 时间线直接显示附件卡片
5. 不再追加“已上传 URL”的系统消息

失败处理：

1. 上传失败时，仅在 composer 附近显示错误
2. 发消息失败时，不向时间线插入假消息
3. 不做本地离线重试队列

## 10. 与 Bridge 的关系

本次虽然先从 Web 侧上传闭环切入，但消息模型一旦扩展完成：

1. bridge ingress 可以发送同样结构的附件消息
2. bridge egress 可以读到完整附件 payload
3. Web 不必区分消息来自人类还是 agent

因此这次改动虽然小，但它补的是通用消息语义层。

## 11. 验证要求

至少验证：

1. 纯附件消息可以创建成功
2. 无正文且无附件时报 `400`
3. 返回事件中的附件已绑定 canonical `messageId`
4. Web 上传后出现附件卡片，而不是 URL 系统提示
5. 图片类附件展示预览与元信息
