# 多智能体协作台 Bridge 附件消息一致性设计规格

- 项目路径：`/mnt/f/ClawWorkspace/09-多智能体协作台`

  - `docs/2026-04-15-多智能体协作台-设计规格.md`
  - `docs/2026-04-30-多智能体协作台-主线复核补记.md`
- 当前目标：让 bridge `attachment send` 与 Web 人类上传回到统一的正式附件消息模型

## 2026-05-09 状态更新

本规格目标已经在当前 `main` 中完成：

1. bridge ingress `message` 支持 `body + attachments`
2. shared bridge client 支持 `attachments`
3. Codex / OpenClaw `attachment send` 会上传文件后发送正式附件消息
4. `caption` 进入消息 `body`
5. 附件 URL 只保存在 `attachments[].url`，不再拼进普通正文
6. bridge egress 可以读回完整附件 payload
7. Web 时间线按附件卡展示，图片使用受控缩略图

本文件保留为附件一致性设计记录，不需要重新执行同名计划。

## 1. 问题

本规格编写时，平台已经出现附件语义分叉：

1. Web 人类上传：
   - 上传后直接创建 canonical message
   - 时间线按正式附件消息渲染
2. bridge `attachment send`：
   - 先 `uploadFile()`
   - 再把 `caption + URL` 拼进 `body`
   - 作为普通文本消息发送

这与原始规格中“统一使用消息 + 附件模型”的方向不一致。

## 2. 本次目标

本次只补桥接附件一致性：

1. bridge `attachment send` 发送正式附件消息
2. `--caption` 写入同一条消息的 `body`
3. 不再把附件 URL 拼进正文
4. bridge egress 拉回来的 event 直接包含 `attachments`
5. README 与当前实现对齐

## 3. 非目标

本次不进入：

1. 多附件批量发送
2. bridge 侧图片缩略图或媒体转码
3. 权限签名 URL
4. 新建独立附件消息路由
5. 额外 UI 设计变更

## 4. 方案比较

### 方案 A：扩展现有 `/api/bridge/ingress/message`

做法：

1. ingress `message` 接口支持可选 `attachments`
2. `BridgeService.sendMessage()` 将 `body + attachments` 一起送入现有 canonical message pipeline
3. shared client 与 runtime 按新字段发送

优点：

1. 与 Web、人类 API、bridge 三条链路保持同一消息模型
2. egress 不需要新协议
3. 语义统一，后续维护最低

### 方案 B：新增 bridge 专用附件消息入口

优点：

1. 对现有 `message` 路由侵入较小

缺点：

1. 再次引入消息语义分叉
2. 以后仍要回收为统一模型

### 方案 C：保留文本 URL 兼容，服务端做字符串猜测

缺点：

1. 将正式附件消息重新降级成约定俗成字符串协议
2. 不可维护
3. 直接违背本次主线修正目标

## 5. 选型结论

采用方案 A：

1. bridge ingress 直接支持可选 `attachments`
2. `body` 可为空字符串
3. `body` 与 `attachments` 至少一个存在
4. bridge runtime 上传成功后发送 `sendMessage({ body, attachments })`

## 6. 行为定义

### 6.1 CLI 行为

`attachment send --file <path> [--caption <text>]`

升级后：

1. 先上传文件
2. 再发送正式消息
3. 若带 `--caption`，写入 `body`
4. 若不带 `--caption`，发送纯附件消息

### 6.2 服务端行为

`POST /api/bridge/ingress/message`

支持字段：

1. `sessionId?`
2. `agentId`
3. `displayName?`
4. `capabilities?`
5. `roomId`
6. `body`
7. `attachments?`

约束：

1. `body` 可以为空字符串
2. `attachments` 为可选数组
3. `body.trim()` 为空且 `attachments` 为空时返回 `400`

### 6.3 Egress 行为

不新增新接口。

理由：

1. egress 本来就是回放 canonical room events
2. 只要 ingress 写入的是正式附件消息，egress 自然会返回完整 `attachments`

## 7. 验证要求

至少验证：

1. bridge ingress 支持“正文 + 附件”消息
2. shared bridge client 能发送 `attachments`
3. codex runtime 的 `attachment send` 不再发送 URL 文本消息
4. openclaw runtime 的 `attachment send` 不再发送 URL 文本消息
5. egress 拉回来的 event 中包含 `attachments`
6. README 已更新为正式附件消息说明
