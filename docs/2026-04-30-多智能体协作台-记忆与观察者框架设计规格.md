## 1. 背景与定位

当前实现已经具备：

1. `L1` 原始房间事件日志
2. `L0` 轻量工作记忆
3. 摘要快照入口
4. 规则型 `Observer` 骨架

但仍缺少真正可长期演进的记忆主框架：

1. `Observer` 的回写范围没有被明确约束
2. 候选层与确认链路没有实体化
3. `L2` 共享知识与 `L3` 私有记忆还没有稳定边界
4. “私有经验如何在人工确认后进入共享层”没有可执行主链路

本规格定义的是下一阶段骨架，而不是在当前 `Phase 1B` 上做零散补丁。

## 2. 设计目标

本阶段要解决的核心问题：

1. 所有消息、附件、桥接事件继续保持“先写事实，再做派生”
2. `Observer / Curator` 允许产出回写内容，但只能写入候选层或私有层
3. 为共享候选、共享知识、Agent 私有记忆建立清晰数据对象和权限边界
4. 让 `L3` 从“仅概念存在”变成“真实可写、可读、可提交候选”的最小可用版
5. 保证将来可以把当前 in-process 处理平滑替换为异步后台 worker，而不推翻接口

## 3. 本阶段不做的内容

以下内容不进入本规格对应的第一轮实现：

1. 向量检索、embedding、召回排序
2. 自动把私有记忆直接提升为共享知识
3. 复杂图谱、关系网络或跨房间推理引擎
4. Observer 主动发言、自主检索执行器、自治编排器
5. 重型数据库迁移，本阶段仍基于文件型持久化
6. 面向普通用户的完整可视化后台，本阶段只要求管理 API 可用，Web 面板只做后续最小补充

## 4. 方案比较

### 4.1 方案 A：事件主链 + 派生层解耦

所有事实先落 `L1`，再由独立派生层刷新 `L0`、产出共享候选、写入 `L3` 私有记忆。

优点：

1. 与“先保真，后提炼”的主线完全一致
2. 原始事实与候选回写天然隔离
3. 未来替换为后台异步 worker 时成本最低

缺点：

1. 引入额外的派生编排层
2. 初期实现会比“在消息服务里顺手双写”更繁琐

### 4.2 方案 B：消息服务同步双写所有记忆层

优点：

1. 实现快
2. 表面上看链路简单

缺点：

1. `MessageService` 会迅速膨胀
2. 记忆策略与主消息链路过度耦合
3. 后续演化成本高

### 4.3 方案 C：Observer 全权编排

优点：

1. 职责看起来集中
2. 便于把所有派生逻辑放在一个入口

缺点：

1. `Observer` 会演变为超大中心模块
2. “检测”“私有沉淀”“共享候选”“知识沉淀”混成一团
3. 边界反而更难拆

## 5. 选型结论

本阶段采用 `方案 A：事件主链 + 派生层解耦`。

结论如下：

1. `L1` 事件层仍是唯一事实源
2. `L0`、共享候选层、`L2`、`L3` 都属于派生层
3. `Observer` 不直接改写事实层，只能写候选或私有沉淀
4. 人工确认仍然是共享层提升的硬边界

## 6. 总体架构

本阶段把记忆与观察者框架固定为六层：

### 6.1 L1 事实事件层

职责：

1. 保存消息、附件、参与者、bridge、记忆操作等原始事件
2. 作为所有派生行为的唯一事实来源

约束：

1. 只追加，不覆盖
2. 不允许摘要、待办、决策等派生结果直接替代事实

### 6.2 L0 房间工作记忆层

职责：

1. 保存房间热上下文
2. 为当前房间协作提供快速视图

内容包括：

1. 最近消息窗口
2. 当前活跃参与者
3. 当前待办
4. 当前阻塞项
5. 当前决策摘要
6. 当前最新摘要草稿引用

### 6.3 Observer / Curator 派生层

职责：

1. 只读 `L1` 与必要的 `L0`
2. 产出摘要草稿、待办候选、阻塞项候选、决策候选
3. 为单个 Agent 写入私有沉淀

约束：

1. 不直接改写 `L1`
2. 不直接生成最终共享知识
3. 不得越权读取或写入其他 Agent 的私有层

### 6.4 共享候选层

这是混合式架构的关键缓冲层。

职责：

1. 接收 `Observer` 产出的共享候选
2. 接收 Agent 从 `L3` 提交上来的共享候选
3. 等待人工确认、拒绝或过期

内容范围固定为：

1. 摘要草稿
2. 待办候选
3. 阻塞项候选
4. 决策候选

### 6.5 L2 共享知识层

职责：

1. 保存已经被接受的共享沉淀
2. 面向跨天、跨会话、跨房间复用

第一版仅允许：

1. `decision`
2. `fact`
3. `constraint`
4. `todo`

### 6.6 L3 Agent 私有记忆层

职责：

1. 为单个 Agent 保存私有笔记、偏好、任务上下文、观察结论
2. 支持 Agent 读写自己的私有沉淀
3. 支持 Agent 把片段提交为共享候选

关键约束：

1. 私有记忆默认只允许所属 Agent 可读写
2. 私有记忆不能直接进入 `L2`
3. 只能走“私有记忆 -> 共享候选 -> 人工确认 -> 共享层”链路

## 7. 核心数据对象

### 7.1 EventRecord

建议在现有 `RoomEventRecord` 基础上扩展为统一事件对象。

字段：

1. `eventId`
2. `roomId`
3. `spaceId`
4. `kind`
5. `actorParticipantId`
6. `timestamp`
7. `payload`
8. `source`
9. `causationId`
10. `correlationId`

说明：

1. `kind` 至少覆盖：
   - `message.created`
   - `attachment.added`
   - `participant.joined`
   - `participant.left`
   - `bridge.session.connected`
   - `bridge.session.disconnected`
   - `memory.candidate.submitted`
   - `memory.candidate.accepted`
   - `memory.candidate.rejected`
   - `memory.private.saved`
2. `source` 只能是 `human` / `agent` / `bridge` / `system` / `observer`
3. `causationId` 和 `correlationId` 用于把候选、私有记忆、共享知识与原始事件链路串起来

### 7.2 WorkMemoryRecord

在现有房间工作记忆基础上扩展。

字段：

1. `roomId`
2. `recentMessages`
3. `activeParticipantIds`
4. `todoItems`
5. `blockerItems`
6. `decisionItems`
7. `lastSummaryDraftId`
8. `updatedAt`

说明：

1. 这是房间热视图，不是长期事实库
2. 允许覆盖更新
3. 只保存“当前协作窗口里需要快速访问的内容”

### 7.3 MemoryCandidateRecord

这是共享候选层和私有候选层的统一对象。

字段：

1. `candidateId`
2. `roomId`
3. `scope`
4. `candidateType`
5. `title`
6. `body`
7. `status`
8. `proposedBy`
9. `sourceEventIds`
10. `sourceMemoryIds`
11. `targetAgentId`
12. `createdAt`
13. `reviewedAt`
14. `reviewedBy`
15. `acceptedInto`

说明：

1. `scope` 只允许 `shared` 或 `private`
2. `candidateType` 只允许 `summary` / `todo` / `blocker` / `decision`
3. `status` 只允许 `proposed` / `accepted` / `rejected` / `expired`
4. `proposedBy` 允许 `observer`、`agent:<id>`、`human:<id>`
5. `targetAgentId` 仅在私有候选时使用
6. `acceptedInto` 用于标记最终进入 `L0`、`L2` 或两者

### 7.4 SharedKnowledgeRecord

这是 `L2` 的轻量第一版。

字段：

1. `knowledgeId`
2. `spaceId`
3. `roomId`
4. `kind`
5. `title`
6. `body`
7. `keywords`
8. `sourceCandidateId`
9. `sourceEventIds`
10. `createdAt`
11. `updatedAt`

说明：

1. 第一版不做知识图谱，只做被确认后的共享沉淀
2. `kind` 先限制在 `decision` / `fact` / `constraint` / `todo`

### 7.5 PrivateMemoryRecord

这是 `L3` 的最小可用版。

字段：

1. `memoryId`
2. `agentId`
3. `roomId`
4. `memoryType`
5. `title`
6. `body`
7. `tags`
8. `confidence`
9. `visibility`
10. `sourceEventIds`
11. `createdAt`
12. `updatedAt`
13. `lastReferencedAt`

说明：

1. `visibility` 第一版固定为 `private`
2. `memoryType` 第一版只做 `note` / `preference` / `task-context` / `insight`
3. 必须保留 `sourceEventIds`，否则私有记忆不可追溯

## 8. 关键写入链路

### 8.1 房间消息 / 附件进入平台

链路固定为：

1. 进入 canonical message pipeline
2. 先写 `L1 EventRecord`
3. 同步刷新 `L0 WorkMemoryRecord`
4. 派生层读取增量事件
5. `Observer` 产出共享候选
6. 满足私域规则时写入对应 Agent 的 `L3`

### 8.2 Observer 回写

Observer 只允许执行以下动作：

1. 生成摘要候选
2. 生成待办候选
3. 生成阻塞候选
4. 生成决策候选
5. 为单个 Agent 写入私有沉淀

Observer 禁止执行以下动作：

1. 直接覆盖 `L1`
2. 直接把候选写成共享知识
3. 读取其他 Agent 的 `L3`
4. 直接改变人工身份或 room 事实状态

### 8.3 私有记忆提升为共享候选

固定链路为：

1. Agent 读取自己的 `L3`
2. Agent 选择片段提交为共享候选
3. 系统写入 `MemoryCandidateRecord`
4. 人工审核接受或拒绝
5. 接受后才允许进入 `L0` 或 `L2`

不能跳过人工确认。

### 8.4 候选接受

当候选被人工接受时：

1. 写入 `memory.candidate.accepted` 事件
2. 根据 `candidateType` 决定是否更新 `L0`
3. 根据内容类型决定是否写入 `L2`
4. 保留 `sourceCandidateId`、`sourceEventIds`、`sourceMemoryIds`

## 9. 权限与隔离规则

### 9.1 共享层

1. 人类管理员或当前房间具备管理权限的人类参与者可以审核候选
2. Agent 可以提交共享候选，但不能自行接受
3. Bridge 只能代 Agent 传输，不得绕过身份边界操作共享层

### 9.2 私有层

1. `agent-A` 只能读写 `agent-A` 的 `L3`
2. 人类默认不读取 `L3` 原文
3. 人类能看到的是 Agent 主动提交出来的共享候选，而不是私有层全部内容

### 9.3 Observer

1. Observer 可写共享候选
2. Observer 可写私有沉淀
3. Observer 不具备“最终裁决权”

## 10. 落地形态

本阶段仍采用文件型持久化。

建议新增存储：

1. `data/db/memory-candidates.json`
2. `data/db/shared-knowledge.json`
3. `data/db/private-memories.json`

并保留既有存储：

1. `data/logs/rooms/*.jsonl`
2. `data/db/work-memory.json`
3. `data/db/room-summaries.json`

说明：

1. 第一版优先压稳对象边界和链路
2. 存储后端未来可以替换，但对象模型与权限规则不应重写

## 11. 服务拆分建议

为了避免 `MessageService` 继续膨胀，建议新增独立的记忆编排服务，例如：

1. `MemoryPipelineService`
2. `MemoryCandidateStore`
3. `SharedKnowledgeStore`
4. `PrivateMemoryStore`

职责建议如下：

1. `MessageService` 负责追加事实事件
2. `MemoryPipelineService` 负责把新事件投影到 `L0`，并触发候选与私有沉淀写入
3. `ObserverService` 负责检测和生成候选建议，不直接做最终存储裁决
4. route 层只调用 service，不直接拼持久化规则

## 12. API 边界建议

第一版最小 API 即可满足框架验证：

1. `GET /api/memory-candidates`
2. `POST /api/memory-candidates/:id/accept`
3. `POST /api/memory-candidates/:id/reject`
4. `GET /api/shared-knowledge`
5. `GET /api/private-memories`
6. `POST /api/private-memories`
7. `POST /api/private-memories/:id/share-candidate`

说明：

1. `private-memories` 必须带 `agentId`
2. `memory-candidates` 至少支持 `roomId`、`scope`、`status` 过滤
3. 本阶段先保证 API 可用，不要求完整 Web 面板同时落地

## 13. 失败与一致性要求

必须满足：

1. `L1` 写入失败时，请求整体失败，不允许只更新派生层
2. `L0`、候选层、`L3` 写入失败不得伪装成事实已沉淀
3. `Observer` 失败不得阻断房间消息主链路，但必须留下可追踪错误
4. 私有记忆写入失败不得降级为共享写入
5. 候选接受失败时不得产生半提交状态
6. 任一层的派生错误都不能回滚既有事实层

## 14. 与原始主线的一致性

本规格与原始设计主线保持一致：

1. 原始消息和附件仍先保真
2. 共享层与私有层边界仍然严格分离
3. 私有记忆没有自动上浮为共享知识
4. Observer 仍是规则驱动，不是自治大脑

变化只在于把原本抽象描述的 `L2/L3/Observer` 边界实体化，并把“混合式回写”限制在可控范围内。

## 15. 验证要求

后续实现必须覆盖至少以下验证：

1. 房间消息进入后，事件先落 `L1`，再更新 `L0`
2. Observer 只能生成候选，不得覆盖事件事实
3. 私有记忆只能由所属 Agent 读写
4. Agent 提交共享候选后，必须经过人工接受才能进入共享层
5. 候选被接受后，`L0` 与 `L2` 的目标写入符合 `candidateType`
6. 失败场景下不出现“事实未落库但候选已存在”或“私有写入失败后泄漏到共享层”的错误状态

## 16. 一句话结论

下一阶段的记忆主线应当是：

“所有事实仍先进入 `L1`；Observer 只能受控地产生候选和私有沉淀；`L3` 真实可用，但任何共享化都必须先变成候选，再经过人工确认。”
