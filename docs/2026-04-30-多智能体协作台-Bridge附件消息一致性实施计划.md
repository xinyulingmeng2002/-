# 多智能体协作台 Bridge 附件消息一致性 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让 bridge `attachment send` 与 Web 上传保持同一正式附件消息模型，不再把 URL 拼进普通文本消息。

**Architecture:** 继续沿用当前 canonical message pipeline，不新增 bridge 专用附件路由。服务端扩展 `bridge ingress/message` 支持可选 `attachments`，shared client 与 codex/openclaw runtime 统一发送 `body + attachments`。

**Tech Stack:** Node.js 22, npm workspaces, TypeScript, Fastify, React, Vitest, Zod

---

## Scope Decision

本计划只覆盖：

1. bridge ingress `message` 支持可选 `attachments`
2. shared bridge client 发送 `attachments`
3. codex/openclaw `attachment send` 升级为正式附件消息
4. README 对齐当前附件模型

以下内容明确不进入本计划：

1. 多附件批量发送
2. 新的 bridge 附件专用路由
3. 新的前端卡片样式设计
4. 附件签名 URL

## Implementation Notes

1. 不新增新的 ingress 路由，直接扩展 `/api/bridge/ingress/message`。
2. bridge runtime 不再格式化 `caption + url` 文本。
3. `caption` 进入正式消息的 `body`，URL 仅存在于 `attachments`。
4. egress 只验证回放结果，不单独造协议。
