## 1. 复核目的

在继续推进下一步实现前，重新核对：

1. 最初设想的主线是否仍然成立
2. 当前实现是否已经发生方向性偏移
3. 如果没有偏移，当前最需要收口的局部问题是什么

## 2. 最初设想的稳定主线

根据原始会话与设计冻结稿，可以确认以下主线没有变化：

1. 这是一个通用多 Agent 协作平台，项目文件夹只是放在 `/mnt/f/ClawWorkspace/` 根目录附近，不属于小窝本体，也不依赖小窝内部结构
2. 平台不能把 OpenClaw、Codex 或其他运行时强绑定进核心；OpenClaw / Codex 只是首批示范适配器
3. 项目目标是长期运行的房间式多 Agent 协作平台，用户可以创建多个聊天空间，并按需要接入一个或多个 Agent
4. 身份边界优先，桥接器只负责传输，不代表发言者本体
5. 原始消息、附件和事件必须先保真，再做摘要、知识提炼与长期沉淀
6. v1 应统一使用“消息 + 附件”模型，而不是把多模态退化成文本 URL

## 3. 当前实现与主线的一致处

当前实现仍然与主线保持一致的部分：

1. `apps/server` 继续作为 canonical state，没有被任一 bridge runtime 反向接管
2. `apps/bridges/codex` 与 `apps/bridges/openclaw` 仍是适配器壳，而不是平台核心
3. 房间、参与者、token、session、ingress、egress、summary snapshot 等骨架已经成形
4. 平台仍保持“先把长期协作底座搭稳，再逐步补强能力层”的阶段策略

结论：

当前没有发生“项目变成 OpenClaw 附庸”或“项目反过来开始重构小窝本体”这类主线级偏移。但后续文档和实现必须继续使用更严格的独立平台口径：它不是小窝旁侧模块，也不是默认为小窝 / Telegram / OpenClaw 服务的基础设施；这些系统如果未来接入，只能作为普通外部 adapter 示例。

## 4. 当前出现的局部分叉

虽然主线未偏，但当时已经出现两处需要及时收口的局部分叉。2026-05-09 复核时，这两处已经在当前 `main` 中收口：

### 4.1 附件语义分叉

Web 人类上传链路已经进入正式附件消息模型：

1. 上传后直接创建 canonical message
2. 时间线按附件卡片渲染

当时 bridge 侧附件发送仍然是：

1. `uploadFile()`
2. 再把 `caption + URL` 拼进 `body`
3. 作为普通文本消息发送

这会造成：

1. 人类消息与 Agent 消息在附件语义上不一致
2. 时间线出现两套行为
3. 原始规格中的“统一消息 + 附件模型”被局部打断

### 4.2 文档语义落后

当时 README 仍保留“上传附件后把 URL 作为 canonical message 发进房间”的旧说明。

这与当时 Web 侧已经提交的正式附件消息实现不一致，会误导后续开发和复核。

## 5. 是否发生主线偏移

本轮判断：

1. 没有发生主线级偏移
2. 发生的是“阶段性实现不均衡”和“局部语义分叉”

更准确地说：

1. bridge 骨架推进得比较深
2. 统一附件语义刚开始收口
3. 记忆、沉淀、后台学习仍处于轻量骨架阶段

这属于完成度结构偏斜，不属于目标替换。

## 6. 当前最优先的修正点

在继续新增能力前，当前最应该先收口的是：

1. bridge 附件发送与 Web 附件消息模型统一
2. README 与当前实现重新对齐

推荐的下一步表述应为：

“继续保持独立协作底座路线，但优先收拢附件语义，让人类上传和 bridge 发送都回到统一的正式附件消息模型。”

## 7. 本次复核结论

一句话结论：

主线没有偏，当前该修的不是方向，而是附件语义分叉。
